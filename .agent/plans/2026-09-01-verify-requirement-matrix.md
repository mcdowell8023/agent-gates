# CHECK 6 改造：验收 = 需求遗漏检查

> v4（2026-09-01）—— 三轮异构审查后定稿：
> gemini-3.1-pro 7 条（→ v2）、gpt-5.4 6 条（→ v3）、gpt-5.4 复审 mixed-layer 1 条（→ v4）。
> v3 经 gemini 复审 PASS；v4 的改动方向是**放宽**，用于消除 v3 的一处误伤。修订记录见 §7。

## 1. 问题定义

verify（CHECK 6）的目的是**发现需求遗漏**，不是第二次代码审查。
用户给的两个真实失败形态：

- **纵向漏层**：后端接口写了，前端一行没写 → 用户根本用不了
- **横向漏项**：需求「导出全部表格内容」，搜索做了，导出接口没写

两者共同属性：**漏做在 diff 里不留痕迹**。

| 检查方式 | 对漏做是否有效 | 原因 |
|---|---|---|
| CHECK 5 代码审查 | ❌ | 读的是 diff；没写的东西不在 diff 里，存在的每一行都是对的 → PASS |
| jest / 单测报告 | ❌ | 测试由实现者自己写；没做的部分自然没写测试。**测试全绿与需求少一半可以同时成立** |
| 覆盖率 | ❌ | 分母同样由代码派生 |
| 逐条对照需求清单 | ✅ | 清单来自需求，漏的那条会空着 |

**唯一判据：清单必须来自需求，不能来自代码。** 一切从代码派生的清单（diff、测试、覆盖率）
对漏做结构性失明。

## 2. 目标的准确表述（v2 修正）

⛔ 目标**不是**「无法绕过」。铁了心撒谎的模型总能撒谎：把漏做的条目标成 `NA`、
`DEFERRED`，或者给一条编造的理由。想做到防这个，只会造出一堆假失败，
而假失败正是门禁失去信任的原因（用户刚说过审查是卡点）。

✅ 目标是「**无法静默绕过**」：

1. 每一条需求都必须有一个**明确处置**（COVERED / PREEXISTING / PARTIAL / DEFERRED / NA / MISSING）
2. 条目数由工具从需求源数出来，**模型无权决定有几条**
3. 所有逃逸口（NA / DEFERRED / PREEXISTING）**计数并打印在结论里**，异常数量肉眼可见

即：把「悄悄少做一半」变成「必须写下来说我少做了什么」。

### 2.1 门禁管形式，异构审查管实质（v3 新增）

gpt-5.4 的核心反驳成立：门禁**能检查「有没有给每条需求填一行」，不能可靠检查
「这行证据是不是真把该需求做完了」**。后者是语义判断，shell 脚本做不到。

所以分工必须写明，不能含混：

| 层 | 负责什么 | 机制 |
|---|---|---|
| 门禁（本改造） | **形式** —— 条数对得上、每条有处置、引用落在本次改动内、层面声明齐全 | E1–E6，确定性可测 |
| 异构验收模型 | **实质** —— 这条证据是否真的完成了这条需求 | 家族 != 实现者，逐条作答 |

门禁的贡献不是「判断对不对」，而是**让验收模型无法静默跳过任何一条**，
并且它的每一条回答都落在可追溯的位置上。

⛔ 不声称：门禁能识别「证据看着对其实不对」。这项永远依赖模型，
门禁只保证这个模型是异构的、且被逼着逐条回答。

## 3. 现状与缺口

`templates/verifier.md` 已经写了「验收标准是否逐条满足」。门禁没有任何机制检查「逐条」：

CHECK 6 实际只校验：
1. `^VERIFY_VERDICT:[[:space:]]*(PASS|FAIL|QUESTIONS|INCOMPLETE)` 存在
2. `<run-id>.dispatch.json` 的 `staged_diff_hash` 锚定当前 staged diff
3. high-risk + EVIDENCE_ONLY → PASS 降级 INCOMPLETE

散文 + 一行 PASS 即可通过。这就是它退化成第二次代码审查的机制原因。

需求清单本已在盘上，CHECK 6 从不读：
- `.agent/plans/<topic>.md`（CHECK 3 强制要求）
- `features/*.feature`（CHECK 2 对 Path A 强制要求）

同一形状复发：**承载真相的产物存在，检查点不读它**（对比 v2.6.0 修的 dispatch→CHECK 6 断链）。

## 4. 设计

### 4.1 产物格式

`.agent/verify/<date>-<topic>.md` 增加需求矩阵，每条需求一行：

```
VERIFY_VERDICT: FAIL
REQ_SOURCE: .agent/plans/2026-09-01-export-all.md
REQ_BLOCK_SHA256: 3f2a...          # 只哈希提取出的条目块，不哈希整个文件
REQ_ITEMS: 3

REQ_ITEM: 1 | COVERED     | src/pages/List.vue:88          | 搜索框已接 GET /api/list?q=
REQ_ITEM: 2 | MISSING     | -                              | 无 /api/export 路由，前端无导出入口
REQ_ITEM: 3 | PREEXISTING | src/pages/List.vue:12          | 分页本次未改动，沿用既有实现
```

### 4.2 状态取值（v2 扩充）

| 状态 | 含义 | 证据要求 | 影响判定 |
|---|---|---|---|
| `COVERED` | 本次改动实现 | 引用路径**必须在本次 staged diff 内** | — |
| `PREEXISTING` | 既有代码已覆盖，本次未动 | 路径在工作树存在即可 | 计数打印 |
| `PARTIAL` | 做了一部分 | 同 COVERED + 必须写清缺什么 | → QUESTIONS |
| `DEFERRED` | 明确不在本次范围 | 必须给去向（下个 PR / issue 号） | 计数打印 |
| `NA` | 不适用 | 必须给理由 | 计数打印 |
| `MISSING` | 该做而没做 | 无 | → FAIL |

**`DEFERRED` 是 v2 新增，专为解决 gemini 指出的反向激励**：
若「任一未完成 → FAIL」，开发者会被迫回去删 plan 里的后两条需求才能提交，
反而破坏需求文档的完整性。给出 DEFERRED 后，增量交付无需篡改需求源。

### 4.3 门禁强制（机制而非散文）

按 `feedback-change-the-data-not-the-prose-rule` 的教训：约束钉在数字上，不写进散文。

**E1 条目数由工具提取，不由模型申报**
门禁自己从 `REQ_SOURCE` 数需求条目，与 `REQ_ITEM:` 行数比对。
数量不符 → FAIL，并打印差值和缺哪几号。
→ 阻止「静默丢条目」的核心机制。模型只能填每条的处置，不能决定有几条。

**E2 只哈希条目块，不哈希整个需求文档**（v2 修订）
`REQ_BLOCK_SHA256` = 提取出的条目文本（去首尾空白、统一行尾）的哈希，由门禁重算比对。
→ 事后删减/改写需求条目会失效（这是要防的）；
→ 改需求文档别处的错别字、补背景说明不会失效（v1 会误伤，gemini 打中）。

**E3 `COVERED` 的引用必须落在本次 staged diff 内**（v2 大改）
v1 只要求「文件存在」，被 gemini 一击打穿：漏做功能时把证据指向 `package.json`
这类必定存在的文件即可放行，等于没检查。

v2 规则：`COVERED` 的引用路径必须出现在 `git diff --cached --name-only`（含 A/M/D）。

**v4 修订 —— 状态下沉到每条证据。** gpt-5.4 复审指出 v3 会误伤真完成项：
「UI 按钮早就有，本次只补 api」交付后用户确实能用，该条就是 COVERED；
但 E6 要 `ui:` 证据、E3 又要求 COVERED 的引用在 diff 内，而那个 UI 文件没改
→ 只能被迫降级 QUESTIONS 或歪曲成 PREEXISTING。
根因：**一条 `REQ_ITEM` 只有一个状态，表达不了逐层混合。**

v4 规则：证据路径前加 `~` 表示「既有、本次未改动」：

```
REQ_ITEM: 2 | COVERED | api:src/export.ts:18, ui:~src/List.vue:88 | 按钮已有，本次补接口
```

| 写法 | 校验 |
|---|---|
| `api:src/export.ts:18` | 路径必须在本次 staged diff 内（A/M/D） |
| `ui:~src/List.vue:88` | 路径只需在工作树存在 |

→ 「已有入口 + 本次补下层」可以合法表达，误伤消除；
→ 反造假属性不变：`COVERED` 至少要有一条**不带 `~`** 的证据（否则本次啥也没干），
   门禁对「全 `~` 的 COVERED」计数并打印 `NOTHING_TOUCHED`。

- 删除类需求（「删掉 LegacyExport.vue」）→ 该路径以 D 出现在 diff 里 → 通过（v1 会误伤，gemini 打中）
- 指向 `package.json` 蒙混 → 除非真改了它，否则 FAIL
- 需求由既有代码覆盖 → 用 `PREEXISTING`，路径在工作树存在即可，计数打印
- 非代码需求（数据库索引、第三方平台配置）→ 证据可用 `RUN:` / `EXT:` 前缀替代路径，
  不必编造文件（v1 会逼人造假，gemini 打中）

**E4 判定由门禁推导，不采信模型那行**
任一 MISSING → FAIL；任一 PARTIAL → QUESTIONS；其余 → PASS。
模型申报的 verdict 若比推导结果更宽松，采用推导结果并打印差异。
（compute, don't accept —— 同 verify-import 的锚）

**E5 异构仍然适用**
验收模型家族必须 != 实现者家族。实现者对自己跳过的部分有盲区，自审无意义。

**E6 证据必须按「层面」声明**（v3 新增，直击纵向漏层）
gpt-5.4 指出 v2 仍抓不稳「后端写了前端没写」：既然真改了后端文件，
拿一个真实的后端路径充数即可标 COVERED。

v3 规则：`COVERED` / `PARTIAL` 的证据按层面加前缀，一条需求可多个层面：

```
REQ_ITEM: 2 | COVERED | ui:src/pages/List.vue:120, api:src/server/export.ts:18 | 导出按钮 → GET /api/export
```

层面取值：`ui:`（用户可达入口）· `api:`（接口）· `db:`（持久化/迁移）· `job:`（任务）·
`cfg:`（配置）· `RUN:`（运行产物）· `EXT:`（本仓外，如第三方平台配置）

判定：
- 整个矩阵没有一条可达性证据 → **打印醒目告警**（不降级、不阻断）
  可达性证据包括：`ui:path`、`ui:~path`（入口既有也是入口）、`RUN:`（运行产物直接证明跑通）、
  `EXT:`（可达性在本仓之外）
- ⚠️ v4 修订：此前写的是「降级 QUESTIONS」，与实现不符，且与 §4.6「运行产物是更强证据」自相矛盾
  —— 会误伤「UI 在别的仓」「只能靠 E2E 结果证明可达」的真完成项。实现一直是打印告警，
  以实现为准。残余风险（`RUN:` 路径不受 E3 校验，可被编造）由 `EXTERNAL_ONLY` 计数暴露。
- 整个矩阵零 `ui:` 证据而需求描述含用户动作 → 打印醒目告警
- 纯后端/纯基建需求用 `NO_UI:<理由>` 显式声明，计数打印

⚠️ 为什么只是告警：判断「这条需求是否用户可达类」需要读需求语义，门禁做不到，
硬 FAIL 或降级都会产生假失败。打印把它交给人和验收模型，
同时保证**不可能不声明**。

**附带收益**：这条部分压制 gpt-5.4 提的粒度作弊 ——「实现导出功能」哪怕只算 1 条，
只给后端证据也会因「整个矩阵零可达性证据」被点出来。
⚠️ 不是硬拦：可达性证据也可以是 `RUN:`（跑通了）或 `EXT:`（可达性在本仓外），
所以「只做后端」仍可用一条编造的 `RUN:` 蒙过，代价是它落在 `EXTERNAL_ONLY` 计数里、肉眼可见。

### 4.4 条目提取：用自然章节，不发明语法（v2 大改）

v1 要求需求源写 `<!-- REQ:BEGIN -->` 标记。gemini 的反驳成立且致命：
**强制则没人写，不强制则永远降级为告警、沦为摆设。**

v2 改为按**命名章节**取，这是人本来就会写的 markdown：

| 来源 | 提取规则 |
|---|---|
| `## 验收标准` / `## Acceptance` / `## 验收清单` 章节 | 该章节下的一级列表项，每项一条 |
| `features/*.feature` | 每个 `Scenario:` / `场景:` 一条 |

⛔ 明确不做：数整个 plan 里的 `- [ ]`。那些通常是实现任务而非需求条目，数出来是噪音。

**分档（v2 收紧）**：

| 档 | 条件 | 行为 |
|---|---|---|
| `explicit` | 找到验收章节或 Scenario | 条数权威，数量不符 = FAIL |
| `bad-source` | `REQ_SOURCE:` 显式给了但无法解析 | **FAIL**（v1 会降级成告警，是个绕过口，gemini 打中） |
| `none` | 完全没有需求源 | 严格分支 FAIL（提示补验收章节）；其他分支告警 |

配套：`templates/` 增加带 `## 验收标准` 章节的 plan 模板，让写它零额外成本。

### 4.5 分级（复用 v2.7.0/v2.8.0 已建的分级层）

⚠️ 本改造让 verify 变严，而用户刚抱怨过「反复审查 5 轮拖慢开发」。
若不分级，等于把刚拆掉的卡点重新装回去。

| 场景 | 要求 |
|---|---|
| 小分支单次提交 | 需求只完成一部分，要求全矩阵是错的 → 默认 `merge-only`，不要求 |
| 合并进主业务分支 / test / master | 全矩阵，零 MISSING；PARTIAL/DEFERRED/NA 需理由且计数打印 |
| `relaxed` | 矩阵仍打印 MISSING 清单，但不阻断（与 `relaxed_waive` 语义一致：只豁免「审了但结论不好」，绝不豁免「从没审」） |

### 4.6 运行证据作为更强形式，不作为定义

用户提过「跑浏览器验收」。浏览器/E2E 是**证明可达性的手段之一**，不是 verify 的定义。
证据列接受两种，强弱分级：
- 代码引用（弱）：受 E3 约束
- 运行产物（强）：E2E 结果文件、截图、curl 记录，用 `RUN:` 前缀

⛔ 不复用 `capability` 字段承载这个强弱轴 —— `capability` 现指「通道能否给出判定」，
语义不同，混用会毁掉现有 high-risk 降级逻辑。新开独立字段。

### 4.7 harvest 必须能生成矩阵骨架

`agent-gates-verify-harvest` 从 REQ_SOURCE 生成条目骨架（含正确条数和 `REQ_BLOCK_SHA256`）。
理由：手写 `.md` 就是伪造判定的入口（v2.6.0 已认定过一次）。骨架必须由工具出。

## 6. 已知薄弱点（必须写明，不掩盖）

- **需求源本身漏条**：需求文档没写的东西，矩阵也查不出。上游问题，
  本设计不声称覆盖，只保证「写进需求的不会被静默丢掉」。
- **逃逸口可被滥用**：`NA` / `DEFERRED` / `PREEXISTING` 都能用来掩盖漏做。
  按 §2 的目标定义，这是**接受的代价**：换来的是零假失败。缓解只有可见性
  （三者各自计数打印），不做硬限制。
- **E3 只证明「改过这个文件」，不证明「真能用」**：能抓编造入口和指鹿为马，
  抓不到「入口存在但是空壳」。运行证据（4.6）才覆盖后者，而它不强制。
- **`PREEXISTING` 是最宽的口子**：全标 PREEXISTING 即可让一个啥也没干的改动过关。
  可见性缓解：计数打印；`PREEXISTING` 数 == 总条数时额外告警。
- **拿真实但无关的文件充数**（gpt-5.4 #1）：E3 要求不带 `~` 的引用在本次 diff 内，
  但只做后端时后端文件确实在 diff 里。E6 压制了它 —— 整个矩阵零可达性证据会被点出来。
  残余有两条：前端根本没写时，仍可拿一个既有列表页写成 `ui:~src/List.vue` 冒充入口；
  或者写一条 `RUN:` 冒充「跑通了」（`RUN:` 路径不受 E3 校验）。
  两者都是语义谎言，门禁按 §2.1 不声称能识别；但前者被迫指向一个具体 file:line、
  后者落在 `EXTERNAL_ONLY` 计数里，异构验收模型几秒就能核。**未完全解决，成本已抬高。**
- **verify 前先改需求源**（gpt-5.4 #2）：`REQ_BLOCK_SHA256` 只防「生成矩阵后改需求」，
  防不了「先删掉最难那条再生成矩阵」。
  **根治要把条目块哈希钉进 CHECK 3 的 PLAN_REVIEW 记录**（计划评审时定版）。
  本次不做，但矩阵里预留该字段，CHECK 3 后续可写入后直接比对。列为跟进项。
- **粒度作弊**（gpt-5.4 #4）：需求写粗则 E1 只数到 1 条。E6 部分压制（层面必须齐），
  但「一条需求内部做了 60%」仍只能靠验收模型判断，门禁无能力。
- **停在 merge-only / relaxed 即可绕过**（gpt-5.4 #5）：这是用户明确要求的分级，
  不是缺陷；但必须承认它是一个开着的口子，且 `off` 更是全关。
  缓解：`agent-gates-status` 应打印当前档位，让「现在其实没在审」这件事可见。

## 7. 修订记录

v1 → v2，采纳 gemini-3.1-pro（VERDICT: FAIL）7 条中的 7 条：

| # | 审查意见 | 采纳方式 |
|---|---|---|
| 1 | E3 对删除类需求造成假失败 | 引用改判 staged diff 成员（含 D） |
| 2 | E2 哈希整个文档，改错别字即失效 | 只哈希提取出的条目块 |
| 3 | 非代码需求无文件可引，逼人造假 | 新增 `RUN:` / `EXT:` 证据形式 |

| 5 | `<!-- REQ:BEGIN -->` 违反书写习惯，必成摆设 | 改用 `## 验收标准` 自然章节 + Gherkin |
| 6 | 「任一 MISSING → FAIL」逼人篡改 plan | 新增 `DEFERRED` 状态 |
| 7 | REQ_SOURCE 指向无块文件 → 降级告警 = 绕过口 | 新增 `bad-source` 档，直接 FAIL |

v1 声称 E3「专治前端没写」是过度宣称，第 4 条打穿了它。

v2 → v3，采纳 gpt-5.4（VERDICT: FAIL）6 条：
