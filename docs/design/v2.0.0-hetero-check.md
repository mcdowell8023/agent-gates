## 1. 背景与动机

### 1.1 直接需求
Writer + Reviewer 全过、跑产品却暴露问题（raw headers / 归集失败 / Bot 重复回复）。缺**黑盒验收** Verifier。三角色：Writer（实现+自测）/ Reviewer（白盒审 diff）/ Verifier（黑盒跑产品）。只有 Verifier 拦得住：做错需求 / UI 没还原 / 回归。

### 1.2 暴露的更大问题
"选异构模型检查本方工作"的能力已散落（oc-serve/D6/Gate 2b/reaper），没命名。本版本给它完整骨架：**hetero-check**。

### 1.3 两起真实 OOM 事故（硬约束）
| 事故 | 真凶 | 量级 | 教训 |
|---|---|---|---|
| 1 | `opencode run` 不带 `--attach` 堆叠 serve | 2.7GB → kernel panic | 长驻无界增长 + **裸跑必须堵死** |
| 2 | **`codebuddy --acp`**（持久 ACP server）崩溃循环漏 101 进程树 | 12.5GB（误判 Paseo 误降级）| 崩溃熔断 + **整进程树清理** + 按通道归因 |

> ⚠️ 注意：事故 2 主角是 `codebuddy --acp`（持久守护），**不是**本子系统的派发通道。本子系统派发用 `codebuddy -p`（一次性）。janitor 的整树清理/归因须覆盖**任意** codebuddy 进程树（含别处启动的 stray `--acp`），但 dispatch 通道本身是低危的 `-p`。见 §3.1 / §4.7。

### 1.4 真实验证案例（Hub agent 29e45bab，已发生）
"CRM V1 Verifier 全面验收"，claude/opus high，cwd ~/wb。真跑黑盒：API 查询 + HTTP 状态 + 日志 + branding，复验 5 + 新发现 6（含 P1 `/auth/sign_in` 500），结论"未达标"。实锤：
1. Paseo claude/opus = 可用 FULL 黑盒通道
2. FULL vs INCOMPLETE 真实存在（D5 缺 AWS SSM 无法验，逐条 verdict）
3. 输出是结构化文档，非一句话
4. 同 vendor 照样揪 11 问题 → **Verifier 异构非强制**（§5.1）
5. 跑到一半要 MFA，靠用户盯着才给上 → 动态交互必须设计（§5.4）

## 2. Goals / Non-Goals / 版本策略

### Goals
1. Verifier：定义 + 四态 + 文档化产出 + 动态交互 + gate 强制（CHECK 6）。
2. 散落异构能力重构为 `lib/hetero/`。
3. 资源生命周期层：跨通道，**可执行地**防两起事故。
4. effort 维度：`(model, effort)`。
5. 全部阈值/策略可配置。

### Non-Goals
1. 不管理开发型子 agent（即用即弃只适用 review/verify）。
2. 不引常驻守护（janitor 机会式 + dispatch 注册的一次性 watcher）。
3. 不替用户定 Paseo orchestration 全部映射。
4. **不假装防恶意 agent**（见 §5.3 威胁模型）。

### 版本策略
- 不拆版本，v2.0.0 一次做完，v2.0.1 修补。
- 实现内部止血先行（P1-P3 先落先测）。
- 兼容 shim 留一个 minor（双读旧字段）。

## 3. 架构总览

```
lib/hetero/
├── config.sh     配置: hetero-check.json + env 覆盖
├── discover.sh   发现各通道可用模型/provider
├── select.sh     选异构 (model, effort)
├── dispatch.sh   派发 + 进程组 spawn + 归因标签 + fail-closed + 能力档判定 + Paseo watcher
├── serve.sh      opencode 共享 serve (原 oc-serve.sh)
└── janitor.sh    度量/预算/回收/熔断/归因/墙钟 (横切所有通道)
```

### 3.1 调度层两级优先级
```
dispatch(role, model, effort, prompt, supervised):
  1. Paseo? → orchestration-preferences 取 provider → 异构过滤 + --thinking(effort)
            → create_agent (唯一支持动态交互的通道) + 注册一次性墙钟 watcher(§4.2)
            → review/verify 即用即弃: 完成即 archive; 能力档=FULL
  2. opencode? → select 异构 model + --variant(effort)
            → ★ fail-closed: oc_serve_ensure 拿到 attach URL 才派, 否则禁裸跑降级
            → 单轮, 能力档=EVIDENCE_ONLY (不能黑盒跑产品)
  3. codex? → codex exec -c model_reasoning_effort=<effort>; 能力档=EVIDENCE_ONLY
  4. codebuddy? → codebuddy -p --model <id> (一次性, 低危; 非 --acp); 能力档按是否能跑产品判
  5. 都不行 → claude-code agent (同 vendor 兜底, HETERO_EXHAUSTED)
```
**能力档由 dispatch 层按实际所用通道判定并写入 dispatch 产物**（非 Verifier agent 自报），防伪同 §5.3。

**dispatch 产物契约（r3 补丁，钉死防漂移）**：dispatch 退出前**原子写**（tmp+rename）`.agent/verify/<verify_run_id>.dispatch.json`，含 `{verify_run_id, channel, capability(FULL|EVIDENCE_ONLY), started_at, wall_s, HEAD, staged_diff_hash}`。`verify_run_id` 由 dispatch 在派发前生成（如 `<date>-<topic>-<shorthash>`），**贯穿 verify 文档、`.ack`、dispatch 产物三者**，gate 据此确认三者属同一次验证、绑同一 `HEAD+staged_diff_hash`，杜绝"A 轮文档配 B 轮能力档"错配。**register-before-spawn**：dispatch 必须先登记 `{verify_run_id, root_pid 占位, pgid}` 再 spawn（或 try/finally），避免 spawn→register 间 crash 产生 janitor 不认领的孤儿。

### 3.2 effort 维度（四通道已验证支持）
opencode `--variant high` / codex `-c model_reasoning_effort=high` / paseo `--thinking <id>` / claude-code `effort` 参数。
**按风险分级**：普通 `medium`，高风险（UI/auth/迁移/服务编排）或用户显式 `high`。配置键 `effort.{reviewer,verifier}.{normal,high_risk}`。高风险判定抽**单一共享 helper**（§3.2 effort 与 §6 CHECK 6 触发共用，防漂移）。

## 4. 资源生命周期层（janitor.sh）

### 4.1 度量
- `measure_rss_tree(root_pid)` — sum 整进程树/PGID 的 RSS（单 PID 对多进程 app 严重低估）。
- `measure_age` / `measure_runs`（锁目录计数）。平台降级：RSS 不可用回退 age + run-count。

### 4.2 预算 + 墙钟执行器（修 GLM：原墙钟无执行器）
| 通道 | 上限 | 配置键 |
|---|---|---|
| opencode serve | tree-RSS>1.5GB / age>2h / runs>50 | `HETERO_OC_RSS_MAX_MB`/`_MAX_AGE_S`/`_MAX_RUNS` |
| 所有 agent 通道（含 Paseo）| 墙钟>600s | `HETERO_AGENT_MAX_WALL_S` |

**墙钟执行器**：dispatch.sh 创建 Paseo/agent 时**注册一次性 watcher**（后台 `sleep $WALL && <cancel/archive + PGID kill>`，记 watcher PID 随 agent 生命周期清理）。不靠"dispatch 后"触发（对 hang 住的 agent 永不到）。watcher 自身轻量、不是常驻 daemon。**r3 补丁**：watcher 必须用 `nohup`/`hetero_spawn_pg` 起，否则 dispatch 退出时 watcher 收 SIGHUP 死掉 → 墙钟失效；agent 正常退出时 dispatch 主动 `kill watcher_pid`（idempotent，dispatch 自身 crash 时 watcher 孤儿最多空跑 $WALL 后退出，可接受）。

### 4.3 回收（修 TOCTOU + macOS 进程树）
**TOCTOU**：`.draining` 锁——janitor 回收 serve 前写 `.draining` → dispatch 见到拒绝新 attach（改派/等）→ 等存量归零 → 二次确认 → kill → 删锁。`oc_serve_restart` **必须改为先获 mkdir 锁**（当前未获，实现须改）。
**macOS 进程树**：
- ❌ 禁 `pkill -P`（macOS 不杀孙进程）。
- ✅ spawn 给独立进程组。**setsid 在 macOS 默认不存在**（已实测确认）→ fallback：bash `set -m` 作业控制起新 PGID（已验证可用），或 `perl -e 'use POSIX; POSIX::setsid()'`（已验证）。实现层封装 `hetero_spawn_pg()` 屏蔽差异。
- ✅ `kill -TERM -<PGID>` → 宽限 → `kill -KILL -<PGID>`，整组带孙进程。
- ✅ **绝不复用调用方 shell 的进程组**（否则误杀 orchestrator）。
- ✅ 现有 `lib/oc-serve.sh:59` / `bin/oc-reaper:57` 的 `kill -9 $pid` 实现阶段须替换为 PGID kill。
- ✅ `bin/with-timeout.mjs` 当前只 `child.kill('SIGKILL')` 不杀子孙 → 须改 `process.kill(-pgid)`，且 spawn 时 `detached:true` 起新组。

### 4.4 熔断（完整规格）
- key：`channel/provider/model/command`（含 command，区分 `-p` 与 stray `--acp`）。
- "启动即死"：`exited_at - started_at < COLD_START_S`（默认 10s）且非零退出。
- 阈值：连续 `crash_loop_max`（默认 3）→ 本会话停用该 key + 降级 + 报警。
- 冷却：距上次失败 `> cooldown_s`（默认 300s）计数清零。
- 每次 spawn 记录 `started_at/exited_at/exit_code/rss_peak/root_pid/pgid`（锁目录）。

### 4.5 归因
spawn 打标签 env `HETERO_SPAWNED=1` + 锁目录登记 `{key, root_pid, pgid, started_at}`。janitor 只认领自己登记的进程树，不误杀、不归错责（事故 2 误判 Paseo 的教训）。

### 4.6 触发时机
dispatch 前（health + budget，`ps`/`curl -m 2` sub-ms）；dispatch 后（临时通道完成即拆）；**Paseo hang 由 §4.2 一次性 watcher 兜**（不依赖 dispatch 后）；可选 schedule 心跳默认关。

### 4.7 codebuddy 生命周期
- 派发通道是 `codebuddy -p --model <id>`（一次性，进程退出，低危）。
- janitor 的 PGID 整树清理 + 熔断 + 归因覆盖**任意** codebuddy 进程树，**含别处启动的 stray `--acp`**（事故 2 主角），按 §4.4 key（含 command）区分。
- 测试：`tests/run_hetero_janitor.sh` 必须含**真实 fork 孙进程**用例，验证整组被收无孤儿。

## 5. Verifier 角色

### 5.1 异构口径 A'
文章 verifier.md 用 `model: inherit`，明说角色价值在**视角分离（黑盒 vs 白盒）非模型异构**；Hub 真实案例同 vendor 揪 11 问题印证。客观行为缺陷与 vendor 无关，主观需求理解异构才有用。
**口径**：Verifier 异构**优先非强制**；gate 卡**能力档（FULL/EVIDENCE_ONLY）不卡 vendor**；Reviewer 强制异构（红线 #8）不变；独立性靠独立子 agent（独立 context）。

### 5.2 verifier.md（新建 ~/.claude/agents/verifier.md）
tools: Read/Grep/Glob/Bash；model: inherit（A'）；system prompt = 文章验收负责人角色 + §5.4 模式协议（监督/非监督 + turn-terminating marker）+ **明确不写 USER_ACK**（§5.3）。

### 5.3 四态结论 + gate + USER_ACK 防伪（方案 A）
| verdict | gate 行为 |
|---|---|
| PASS | ✅ 放行 |
| FAIL | ❌ block——回去修（非确认能过）|
| QUESTIONS / INCOMPLETE | ⏸️ 需 USER_ACK 才放行（打断等用户确认）|

**打断两层**：workflow 层 orchestrator AskUserQuestion 摆清单/原因等指示；CLI gate 层查 USER_ACK。

**USER_ACK 防伪 = 方案 A（r3 收口：hook 工具侧写）**：
- ACK 写**独立文件** `.agent/verify/<verify_run_id>.ack`（不在 agent 写的 verify 文档里），由 **AskUserQuestion 的 PostToolUse hook 工具侧写入**——hook 在真实人类往返完成时触发，带人类实际答案，**LLM（含 orchestrator）不经真实 AskUserQuestion 拿不到 ACK**。这堵住 r3 发现的"偷懒 orchestrator 跳过 AskUserQuestion 直接写 ACK"洞（orchestrator 也是带 Bash 的 LLM，不能信它自觉）。
- ACK 内容绑 `verify_run_id + staged-diff-hash + HEAD`；改代码 → hash 变 → 旧 ACK 失效；commit → HEAD 变 → 失效。
- **`.ack` 不进 git staged**；`staged-diff-hash` **只覆盖业务文件，排除 `.agent/verify/*`**（否则写 ACK 改变它要绑的 hash，鸡生蛋）。gate 读工作区 `.ack`，不要求提交。
- verifier.md / §9B **从不指示任何 agent 写 ACK**；保存 verify 文档的 wrapper **strip 掉 agent 输出里任何 USER_ACK 串**。
- gate 验 ACK：文件存在 + `verify_run_id` 匹配本次 verify 文档/dispatch 产物 + diff-hash 匹配当前 staged（业务文件）+ HEAD 匹配 + mtime ≤ 4h。
- **威胁模型（写进文档）**：本机制只防**偷懒/幻觉 agent 自我放行**，**不假装防恶意 agent**——恶意 agent 能 `--no-verify`/禁 hook，纯本地无解（不引 HMAC，论证见设计评审记录）。真要突破上限的唯一杠杆是**把 gate 挪到服务端/CI**（agent 关不掉），属另一架构，真做时再设计，本版不预埋。
- **能力档同样防伪**：FULL/EVIDENCE_ONLY 由 **dispatch 层按实际通道写入 dispatch 产物**，非 Verifier agent 自报；gate 从 dispatch 产物读，不从 agent 文档读。
- **`required_capability`（r3 补丁，防 EVIDENCE_ONLY 假装黑盒验收）**：高风险场景（UI/auth/迁移/服务编排，用 §3.2 共享 helper 判定）`required_capability=FULL`。若实际只有 `EVIDENCE_ONLY`（无 Paseo，opencode/codex 单轮没真跑产品）：**不得用 EVIDENCE_ONLY 的 PASS 直接放行**，强制降为 `INCOMPLETE`（提示"高风险需 FULL 黑盒验收，请监督模式重跑"）→ 需 USER_ACK 才过。EVIDENCE_ONLY 的 PASS 只对非高风险/非运行类验收直接有效。

**自修复开关**：`VERIFY_SELF_REPAIR_MAX` 默认 0（停等人）；设 N 开启自修 N 次再停。FAIL/INCOMPLETE 可自修；**QUESTIONS 无视开关永远停**（缺需求澄清 agent 修不了）。对齐 §11 三次失败规则。

### 5.4 动态交互机制
**条件分两类**：静态密钥/环境 → dispatch 派前配好注入 env，Verifier 不问；动态交互（MFA TOTP、一次性确认）→ 需活人。
**只有 Paseo 支持动态交互**（opencode/codex 一次性批跑无法中途注入 → 天然非监督，撞交互即 INCOMPLETE）。
**监督 vs 非监督 = 调用链最顶层有无可达活人**（派发 flag 下传，默认**非监督**不卡死）：
```
监督 (顶层交互会话能 AskUserQuestion):
  撞 MFA → Verifier 输出 "VERIFY_NEEDS_INPUT: ..." 作为本轮【最后输出】并【立即让出/结束本轮】
         (优先用 Paseo 原生 pending-input/permission 原语作中继信号; 退化才用字符串 marker)
  → 中继信号触发 orchestrator → AskUserQuestion → send_agent_prompt(答案) → 续跑
  → 墙钟超时没人应 → cancel/archive(PGID kill) → INCOMPLETE: timed_out
非监督 (headless 无可达人):
  preflight 声明交互需求 → 撞交互直接 VERIFY_VERDICT: INCOMPLETE + NEEDS[aws-mfa] 不等
```
**marker 必须 turn-terminating**（修竞态）：agent 输出 marker 后**立即结束本轮**，marker 是本轮最后输出；否则 mid-stream idle 不触发 notify → 卡死。
**P0 spike 已验（2026-06-22）**：Paseo **没有**传值的原生 pending-input 原语——`paseo permit` 仅 `allow/deny`（二元工具审批，不承载 MFA 值）。故**值中继定为字符串 marker + `paseo send <id> "<value>"`**（turn-terminating marker 是主路径，非 fallback）；`permit allow/deny` 仅用于二元工具审批门控。循环：marker 结束本轮 → `notifyOnFinish` → orchestrator 读 marker → `paseo send` 传值 → 续跑。
**MFA 安全**（修泄漏）：动态通道**只准一次性 TOTP / 确认串，禁静态密钥**（静态密钥走 §5.4 静态 env 路径）。`send_agent_prompt` 内容会进 **Paseo session transcript（持久化）**——对一次性 TOTP（30s 失效）可接受并写明；evidence 只记 `NEEDS[aws-mfa] — 已交互提供`，绝不落码。
**中继锚点**：默认派发 Verifier 的交互主会话即锚点（本版本）。

### 5.5 文档化产出
- 完整发现写 `.agent/verify/<date>-<topic>.md`（**独立目录**，避开 CHECK 5 glob）。
- 结构抄 Hub 报告：已知复验表 + 新发现表（P1/P2/P3+证据+复现）+ 逐条 verdict + 结论 + 下一步。
- 回开发会话**只**给 verdict + 计数 + 路径 + 三五行摘要（不撑爆上下文）。
- 留痕：带时间戳每轮一份，支持"上轮 FAIL 这轮修没修好"diff。
- gate 从该文档读 `VERIFY_VERDICT`；从独立 `.ack` 读 USER_ACK；从 dispatch 产物读能力档。

- 触发：复用 CHECK 5 阈值 + 高风险强制（共享 §3.2 helper）。
- verdict：PASS 放行 / FAIL block / QUESTIONS·INCOMPLETE 需 `.ack`（方案 A 校验）放行否则 block。
- 能力档：从 dispatch 产物读（不卡 vendor）。非高风险：FULL 与 EVIDENCE_ONLY 都算有效验收。**高风险（`required_capability=FULL`）：EVIDENCE_ONLY 不能直接 PASS 放行，降 INCOMPLETE+需 ACK**（§5.3）。
- 新鲜度：mtime ≤ 4h，post-verify 改动 ≤ 20 行。**已知限制**：mtime 秒级粒度的同秒竞态（沿用 CHECK 5 已记限制，不可移植地修）。
- 跳过：`SKIP_VERIFY=1` / merge / 新项目首 commit / Trivial。

## 12. 实现前 spike（P0，开发第一步先验证，三家 r3 提）
1. **Paseo 是否真有 pending-input / permission 原语**（§5.4 中继首选路径）——若无，"race-free 原生信号"是 vaporware，只能退到字符串 turn-terminating marker（依赖 agent 合规）。先 spike 确认 Paseo API（`list_pending_permissions`/`respond_to_permission`/`send_agent_prompt` 的 idle 通知行为）。
2. **`codebuddy -p` 是否支持 `--model`** —— ✅ 已验证支持（`codebuddy -p --model glm-5.2` 实测可用）。
3. **`set -m` 在脚本内起新 PGID** 须 `2>/dev/null`/`disown` 抑制作业控制消息污染 stderr；`perl POSIX::setsid()` 脱离控制终端，交互场景注意。`hetero_spawn_pg()` 封装。
4. **`HETERO_AGENT_MAX_WALL_S=600` 默认值**：Hub "全面验收" 真实耗时可能超 600s，开发期调研真实耗时后再定默认（可配置，先 600 起）。
5. **残留实现风险（不阻塞，记 P2.0.1）**：Verifier 持 Bash 理论上能算 diff-hash 伪造 `.ack`/dispatch 产物——威胁模型（只防偷懒不防恶意）覆盖，真正解是服务端/CI gate（本版不做）；mtime 秒级同秒竞态（沿用 CHECK 5 已记限制）。
